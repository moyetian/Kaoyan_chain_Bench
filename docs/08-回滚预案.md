# 08 · 回滚预案（Rollback Plan）· KaoyanBench v1.0

> 核心原则：**任何上线动作都要有回滚方案。** 上线的每一步，都要先知道怎么退回去。
> 部署工程师：狄云

---

## 0. 一句话总纲

KaoyanBench v1.0 是**纯代码 + 数据资产**型项目，无独立服务、无外部数据库服务。回滚的四个层次：

1. **代码回滚** —— `git` 切回上一个已知良好 commit / tag。
2. **任务集版本回滚** —— 恢复 `benchmark/tasks/**` 与 fixture（**事实源**）。
3. **baseline 回滚** —— 恢复回归基线（防被污染）。
4. **结果与报告清理** —— 删除派生物（`results/`、`reports/`），可重建。

> ⚠️ **数据资产红线**：`benchmark/tasks/**` 与 fixture 是**事实源，绝对不能删**；
> `results/benchmark.db` 是**派生物，可 `rm` 重建**。详见第 5 节。

---

## 1. 回滚触发条件

出现以下任一现象，**立即启动回滚评估**：

| # | 触发条件 | 判定阈值 / 现象 |
|---|---|---|
| T1 | 回归门禁失败 | `kaoyanbench regression` 退出码 = 1（Task Success 降 >5pp / Citation Acc 降 >5pp / Hallucination 升 >3pp） |
| T2 | 核心子命令崩溃 | `validate` / `run` / `report` / `grade` 退出码 = 2，或抛未预期异常 |
| T3 | 任务集校验出现 error | `validate --suite core50` → `error>0` |
| T4 | fixture 篡改 / 失配 | `fixtures check` 非 0；`validate` 报 `fixture hash 不匹配` |
| T5 | 静默错误 | 报告中出现 `unknown` 类别、缺失 degraded 告警但实际降级、HTML 有外链 |
| T6 | 发布产物异常 | smoke 非 6/6、报告四件套缺件、版本号不符 |
| T7 | 安全事件 | 发现子进程能看到 `*_API_KEY`（白名单失效）、路径穿越未被拒 |

## 2. 回滚步骤（按层次）

### 2.1 代码回滚

```bash
cd /workspace/KaoyanBench

# ① 记录当前状态（回滚前留痕，便于事后分析）
git rev-parse HEAD                      # 记下当前 commit
git status                              # 确认工作区是否有未提交改动

# ② 切回上一个已知良好版本（二选一）
#   a) 如果有 tag：
git checkout v1.0.0                     # 或上一个良好 tag
#   b) 如果只有 commit：
git checkout <LAST_GOOD_COMMIT>

# ③ 重装（editable 安装可能需要刷新入口）
pip install -e .

# ④ 验证版本
kaoyanbench --version
```

> ⚠️ **危险操作**：`git reset --hard` / `git checkout --` 会**丢弃未提交改动**。
> 回滚前必须先 `git stash` 或 `git worktree` 备份，**不得直接 reset**。

### 2.2 任务集版本回滚（数据资产，谨慎）

任务集变更通常伴随版本号升级。回滚任务集必须**与代码版本配套**：

```bash
# ① 确认当前任务集版本
kaoyanbench list --suite core50 --json | python3 -c "import json,sys;print('tasks=',len(json.load(sys.stdin)['tasks']))"

# ② 用 git 恢复任务集（若任务集在版本控制中）
git checkout <LAST_GOOD_COMMIT> -- benchmark/tasks benchmark/fixtures

# ③ 重新生成 fixture 并校验
kaoyanbench fixtures build
kaoyanbench fixtures check
kaoyanbench validate --suite core50        # 期望 error=0
```

> ⚠️ 若任务集不在版本控制内（如本地生成），必须先有**备份归档**才能回滚。
> **回滚前务必确认已备份 `benchmark/tasks/**`**。

### 2.3 baseline 回滚（防污染）

R9 规定：`grader_mode=degraded` 的结果**不得写入 baseline**。若误写入，需回滚 baseline：

```bash
# baseline 存放位置（CI 约定）
ls -l results/baseline/

# 恢复上一个良好 baseline（若已提交到 git）
git checkout <LAST_GOOD_COMMIT> -- results/baseline/

# 或重新用一次「确定 full 模式」的运行重建 baseline
kaoyanbench run --suite smoke --agent mock --tag baseline-rebuild --seed 42
# 确认 grader_mode=full 后，再将其作为 baseline（人工确认，勿自动覆盖）
```

### 2.4 结果与报告清理（派生物，可重建）

```bash
# 清理运行留痕（SQLite 是派生物；JSONL 视需要保留）
rm -f results/benchmark.db results/benchmark.db-journal

# 如需完全清理：
#   ⚠️ 下面会删除 runs/suites/workspaces —— 仅在确认这些为本次发布产物、且无有用留痕时执行
# rm -rf results/runs results/suites results/workspaces reports/
```

> 恢复：下次运行 / 查询时会自动 `sync_db` 从 JSONL 重建 SQLite；
> suite 结果与报告需**重新 run + report** 生成。

## 3. 回滚后的验证清单

```bash
cd /workspace/KaoyanBench

# 1) 版本回退到位
kaoyanbench --version                     # 期望：回滚目标的版本号

# 2) 安装未错位
python3 -c "import kaoyanbench;print(kaoyanbench.__file__)"   # 指向 /workspace/KaoyanBench

# 3) 单测全绿
python -m pytest tests/ -q                # 期望：274 passed（数字随版本）

# 4) 任务集校验
kaoyanbench validate --suite core50       # 期望：error=0

# 5) fixture 完整
kaoyanbench fixtures check                # 期望：通过 ✅

# 6) 端到端冒烟
kaoyanbench run --suite smoke --agent mock --tag rollback-verify --seed 42
# 期望：6/6 success_rate=100.0%

# 7) 报告可产出
kaoyanbench report --suite smoke --agent mock --tag rollback-verify -f json,markdown,html,csv
ls reports/smoke__mock__rollback-verify/   # 期望四件套

# 8) 回归门禁恢复正常
kaoyanbench regression --baseline deploy-base --current rollback-verify --suite smoke --agent mock
echo "退出码=$?"                           # 期望 0
```

全部通过 → 回滚成功。任一失败 → 按第 4 节「升级处理」。

## 4. 回滚耗时与升级

| 层次 | 预计耗时 | 备注 |
|---|---|---|
| 代码回滚 | 2–5 分钟 | git checkout + pip install -e . |
| 任务集 + fixture 回滚 | 5–15 分钟 | 取决于 fixture 生成耗时（PDF/XLSX 较慢） |
| baseline 回滚 | 1–3 分钟 | 文件级恢复 |
| 结果/报告清理 | <1 分钟 | rm 派生物 |
| 回滚后验证 | 3–10 分钟 | 含 smoke + 报告 |
| **合计** | **约 15–30 分钟** | 不含重新跑真实 Agent 的时间 |

**升级处理**：若回滚后 `pytest` 仍失败、或 `validate` 仍 error>0、或 smoke 非 6/6 →
停止回滚，保留现场（`git rev-parse HEAD`、`results/`、日志），升级至后端/任务集负责人。

## 5. ★ 数据资产保护（红线）

### 5.1 绝对不能删（事实源 / 需长期保留）

| 路径 | 性质 | 说明 |
|---|---|---|
| `benchmark/tasks/**` | **事实源** | 50 题定义、`task.json`、`expected`、`references/`、`manifest.json` |
| `benchmark/fixtures/**` | **事实源（生成物但需入库）** | 确定性生成的测试数据；删了要重新 `fixtures build`，且 hash 记录在 manifest |
| `benchmark/suites/**` | **事实源** | suite manifest（core50/smoke/private_demo） |
| `benchmark/snapshots/**` | **事实源** | 网页快照（一旦建立，删了需重新联网抓取） |
| `config/**` | **事实源** | 配置（default.yaml、agents、graders） |
| `docs/**` | **事实源** | 方案、规范、部署文档 |
| `src/**`、`cli.py` | **事实源** | 源代码 |
| `tests/**` | **事实源** | 测试 |
| `.github/workflows/**` | **事实源** | CI 配置 |

### 5.2 可以删、可重建（派生物）

| 路径 | 性质 | 重建方式 |
|---|---|---|
| `results/benchmark.db`（+`-journal`） | **派生物** | `rm` 后自动 `sync_db` 从 JSONL 重建 |
| `results/runs/*.jsonl` | 运行留痕 | 删了需重新 run；**除非确认无用，否则建议保留** |
| `results/suites/*.suite.json` | 运行留痕 | 删了需重新 run |
| `results/workspaces/` | 临时工作区 | 运行结束即弃；可安全删除 |
| `reports/` | 报告产物 | `kaoyanbench report ...` 重新生成 |
| `__pycache__/`、`*.py[cod]` | 缓存 | Python 自动重建 |
| `*.egg-info/`、`build/`、`dist/` | 构建产物 | `pip install -e .` 重建 |

### 5.3 危险操作清单（必须显式确认后才可执行）

- ❌ `rm -rf benchmark/` —— **禁止**（删事实源）
- ❌ `rm -rf config/ src/ docs/ tests/` —— **禁止**
- ❌ `rsync --delete` 同步到 `benchmark/` —— **禁止**（会删除目标端多余文件）
- ⚠️ `rm -rf results/` —— 仅删派生物，但仍会丢失运行留痕，**需确认**
- ⚠️ `git reset --hard` / `git clean -fdx` —— **丢弃未保存改动**，**需先备份**
- ⚠️ 修改防火墙规则 / 重启数据库服务 —— v1.0 不涉及，**禁止擅自执行**

## 6. 回滚决策速查

```
现象？
├─ regression 退出码 1 ─────────────→ 2.3 baseline 回滚 + 代码回滚
├─ validate error>0 ────────────────→ 2.2 任务集回滚 + 2.1 代码回滚
├─ fixtures check 失败 ─────────────→ 2.2 恢复 fixture（git checkout）
├─ 子命令崩溃（exit=2）──────────────→ 2.1 代码回滚
├─ baseline 被 degraded 污染 ───────→ 2.3 baseline 回滚
└─ 仅报告/DB 异常 ──────────────────→ 2.4 清理派生物 + 重新 report
```

---

## 7. 预防措施（降低回滚概率）

1. **上线前必跑** `bash tools/release_check.sh`（pytest → validate → smoke → 报告存在性）。
2. **baseline 只由 `grader_mode=full` 的运行更新**（CI 已强制，R9）。
3. **加 tag 再发布**：`git tag v1.0.0`，便于 `git checkout` 精确回滚。
4. **任务集变更必须升 `version` 字段**（方案 R6），使版本可比。
5. **保留最近 N 次 run 留痕**，便于 `compare` 定位回归点。
